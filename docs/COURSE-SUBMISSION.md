## Access for the instructor

Repo is **public** (the course encourages open source).

| Concern | Solution |
|---|---|
| Instructor access | A dedicated account; credentials handed over privately via the submission form — **never in the README**. |

The instructor will log in and find an **empty app** unless seeded: no
history, no charts, nothing that shows the value. Half the application
becomes invisible. See "Seed data" in `docs/PROJECT-BRIEF.md` §9 — the seed
script itself is product infrastructure (it stays in that document); this
note just flags *why* it matters for evaluation specifically.

## Deliverables

The evaluation is asynchronous — the instructor reviews the repo and gives
written feedback. **There is no live defence, so the repository is the
deliverable.** Anything not written in the repo does not exist.

- **README** — problem and thesis in three lines, screenshots/GIF, links to
  the live app and video, quickstart, the autogenerated dependency graph, CI
  badges.
- **`AGENTS.md`** — probably the most-read file. Not a rule dump: architecture
  and dependency rule; non-negotiable invariants; definition of done;
  conventions; and an **"observed anti-patterns"** section grown from real
  corrections (the agent *will* put business logic in components). Commit it
  separately — its history is the learning narrative.
- **`docs/adr/`** — 5–6 short records: Astro+Svelte, Supabase over Turso,
  validated JSON output, catalog as a repo file, nutrition deferred,
  guardrails in the domain, quota → deterministic fallback, health data
  handling.
- **`docs/features/*.md`** — BDD specs (Given/When/Then) written *before*
  implementing. These double as the best possible prompt for the agent: hand
  it the spec, not an improvised description. This demonstrates spec-driven
  development.
- **`docs/ai-workflow.md`** — how the agent was used, what was delegated,
  what was done by hand, what went wrong, how the instructions evolved. An
  honest "where AI cost me time" section is worth more than pure enthusiasm.
- **Video, 3–5 min** — the knee problem in 20s; check-in → adapted workout;
  same user in two states producing two different plans; final minute
  showing the quality gates in action (a commit that breaks a layer rule,
  and the lint stopping it).
- **Conventional Commits**, atomic, telling the story of the build.

## Compliance dosage note

This is a development course, not a law course. Do not overinvest in
compliance work, but do not drop it either — see `docs/PROJECT-BRIEF.md` §11
for the actual scope. It shows product judgement and the project has a
future beyond the course.
