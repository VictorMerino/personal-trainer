# Feature: Prompt construction

Specifies the pure context-assembly function feeding the LLM planners, and
the versioning relationship between prompt and schema. See
`docs/adr/0006-prompt-construction.md` for rationale. Per the project's
testing philosophy, these scenarios test *assembly*, never a live model
response.

## Background

```
Given a UserProfile, a TrainingDecision, a permitted compact exercise list,
  and a HistorySummary already exist for a request
```

## Scenario: The assembled context includes only the compact exercise projection

```
Given a permitted exercise list of catalog entries
When buildPromptContext is called
Then each entry in the assembled context has only id, name, pattern,
  equipment and level
And no other exercise field (jointStress, cues, defaultRestSeconds, etc.)
  is included
```

## Scenario: The assembled context includes only the perPattern history view

```
Given a HistorySummary with both perExercise and perPattern populated
When buildPromptContext is called
Then the assembled context includes perPattern data
And it does not include perExercise data, raw SetLog rows, or any
  per-exercise load/stall detail
```

## Scenario: The assembled context contains no free-text user input

```
Given a PlanRequest built from the MVP's all-button check-in and profile
When buildPromptContext is called
Then every value in the assembled context originates from an enum, number,
  or system-computed field
And no field can be traced back to arbitrary user-typed text
```

## Scenario: buildPromptContext is a pure, deterministic function

```
Given fixed profile, decision, exercise list and history inputs
When buildPromptContext is called twice with the same inputs
Then both calls return deep-equal output
And no network call occurs
```

## Scenario: A stored plan records both schemaVersion and promptVersion independently

```
Given a plan is generated by an LLM planner using PROMPT_VERSION 1 and
  WorkoutPlanSchema version 1
When the plan is persisted
Then it records schemaVersion = 1 and promptVersion = 1 as separate fields
```

## Scenario: A prompt wording change alone does not require a schema version bump

```
Given only the prompt's instruction wording changes, with no change to
  WorkoutPlanSchema
When PROMPT_VERSION is bumped
Then schemaVersion is unchanged
And previously stored plans remain valid against the current schema
```

## Scenario: A schema change requires reviewing whether prompt wording also needs a bump

```
Given WorkoutPlanSchema changes (e.g. a new required field is added)
When schemaVersion is bumped
Then the change is not considered complete until it's confirmed whether
  PROMPT_VERSION also needs bumping to explain the new field to the model
```

## Non-goals (explicitly out of scope)

- Testing against live LLM output — covered by `docs/adr/0002-workout-plan-schema.md`
  and `docs/adr/0005-workout-planner-port.md` instead (schema/business validation,
  fallback-chain behavior).
- Free-text input sanitization design. Out of scope until a free-text
  interaction mode is actually built — see ADR 0006 decision 3.
